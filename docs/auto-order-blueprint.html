0. 五個設計原則

櫃台零額外動作

正常情況下櫃台只做一件新事：看一眼平板、點一下「確認」。快速通道連確認都不用點。

只送「差異」，不重送整張單

每一句話進來，模型只回「加什麼、減什麼、改什麼」。這是即時修改能做到 1 秒內的關鍵。

人永遠是最後一關

系統只產生「草稿單」。送 POS 的動作要嘛櫃台按確認，要嘛系統自動送但留 3 秒可撤銷。

聽不懂就標示，不要猜

每個品項帶信心分數。低信心的項目在平板上變黃，櫃台一眼看到要再問客人。

雲端掛了店還能營業

雲端斷線時平板顯示「手動模式」，櫃台照舊打 POS。系統是輔助，不是必經之路。

2. 六個層次各自負責什麼

感知層

把聲音變成「誰、什麼時候、說了什麼」。

  • 指向性麥克風＋回音／降噪
  • 語音活動偵測（沒人講話就不送雲端）
  • 說話者分離：櫃台 vs 客人（櫃台可用固定聲紋註冊）
  • 客人分組：靜音 > 20 秒或櫃台說「歡迎光臨／下一位」就切新單

理解層

把一句話對照菜單，變成結構化指令。

  • 菜單主庫（Menu_Products）＋ POS 選項群組當成模型的固定知識，放在快取前綴
  • 輸出固定格式：add / remove / set_qty / set_option / replace
  • 每條指令帶信心分數與來源句子
  • 同一模型兩種深度：每句話用低深度快速抽取，核對時用高深度總校對

訂單狀態層

草稿單的唯一真相。

  • 事件溯源：存的是指令流，不是最後結果，隨時可回放與撤銷
  • 每筆品項：基底＋選項＋數量＋信心＋來源時間戳
  • 狀態：聆聽中 → 核對中 → 已確認 → 已出單／已取消

人機確認層

櫃台唯一看得到的東西。

  • 平板單頁：左邊草稿單、右邊最近三句聽寫
  • 變動處高亮 2 秒；低信心項目黃底
  • 三個鍵：確認出單／改一下／作廢
  • 快速通道自動送出時顯示 3 秒倒數可撤銷

POS 整合層

把草稿單翻成 POS 聽得懂的格式。

  • 沿用成本系統已驗證的對齊邏輯（基底品項 ＋ 變體選項 → 菜單品項，反向使用）
  • 套餐（+蛋+飲料）展開成 POS 套餐碼
  • POS 回覆成功／失敗，失敗自動退回「核對中」

營運層

撐住 8 小時不中斷。

  • 看門狗：任一環節 30 秒無心跳自動重啟
  • 斷線降級：平板顯示手動模式，錄音本地暫存
  • 每日報表：辨識率、自動放行率、櫃台修正率、每單成本
  • 音檔不留存，只留文字稿與訂單（保留 30 天供除錯）

4. 快速通道 vs 一般通道

熟客一句話點完、櫃台一個「好」就要出單。快速通道不是另一套系統，只是狀態機多一條捷徑，五個條件同時成立才走。

條件快速通道 自動放行一般通道 櫃台確認
品項對齊每一項都是菜單主庫直接命中有任何一項靠模糊比對
信心分數全部 ≥ 0.9任一項 < 0.9
必選選項醬類、種類、麵類等必選都已明講有必選選項還沒說（櫃台要問）
對話形態客人一到兩句講完，櫃台只回「好／OK」來回超過兩輪或客人有猶豫詞（「還是」「等一下」）
放行方式自動送 POS，平板倒數 3 秒可撤銷櫃台點「確認出單」
目標時間客人講完 → 出單 < 5 秒按確認 → 出單 < 2 秒
預估比例：熟客與單品訂單約佔 3～4 成可走快速通道。第一個月建議關閉自動放行、只顯示「可快速出單」提示，等自動放行的準確率連續兩週 ≥ 98% 再打開。

5. 即時修改怎麼做到

差異指令而非整張單

模型每次只看「最新一句話 ＋ 目前草稿單摘要」，回一到三條指令。輸入短、輸出短，單次回應目標 < 800 毫秒。

核對模式的比對

櫃台複誦時，系統把複誦內容當成「第二份草稿」和原草稿比對；不一致的地方標紅，讓櫃台當場發現自己聽錯。

指代消解

「麵改兩份」「那個沙拉不要了」——模型拿到的草稿單摘要有編號，指令用編號回，不靠品名字串比對。

版本與撤銷

每條指令都有序號；平板「上一步」就是回放到前一版。POS 送出時附上版本號，避免送到舊版。

方式做法優點風險評估
A. 官方 APIPOS 廠商提供下單 API 或第三方外送介接介面，草稿單直接送入最穩、有回覆、可查狀態廠商不一定開放，可能要付費首選

8. 撐住 8 小時、200 筆的營運設計

負載其實不高

200 筆／8 小時 ≈ 每 2.4 分鐘一筆；尖峰約 60 筆／小時。單一櫃台麥克風天生是序列的，不會有並發問題。

只在講話時花錢

8 小時裡真正有對話的約 3～4 小時。語音活動偵測在店內做，靜音不上傳。

看門狗與心跳

麥克風、辨識連線、LLM、平板各自每 10 秒回報心跳；任一環節 30 秒沒回報自動重啟，平板角落顯示綠／黃／紅燈。

斷線降級

雲端斷線：平板切「手動模式」，櫃台照舊打 POS；店內持續錄音暫存，恢復後可補跑供除錯。

每日對帳

下班後比對「系統出單」與「POS 實際訂單」：漏單、多單、品項不符。這份報表決定快速通道要不要開。

隱私與告知

櫃台貼告示「本櫃台錄音用於點餐輔助」。音檔即時處理不落地、文字稿 30 天後刪除。

10. 主要風險與待老闆決定的事

風險：環境噪音與台語

早餐店尖峰很吵、客人講台語或中英夾雜。對策：指向性麥克風、菜單詞庫加權、第一階段人工標註 200 句對話做評測集。

風險：POS 不開放

整個價值有一半在自動出單。對策：第一階段用方式 C 試跑，同時去問廠商 API。

風險：櫃台不信任

平板顯示錯一次，櫃台就不看了。對策：前兩週只顯示不放行，讓櫃台看到它「會跟上」再開自動。

已定 ①：POS 為社守（GeoShop）

成本系統已用 HTTP API 讀取其後台；社守官方有 Uber Eats／線上訂單自動接收通道，要問能否開放給自家系統當方式 A。

已定 ②：先做大德店

跑滿一個月對帳後再複製到岡山。

待決 ③：套餐與加購規則

「+蛋+飲料」的套餐碼、加購價、飲料冷熱甜度，需要一份櫃台實際的點法清單。

11. 分階段落地

第 0 階段 · 2 週
錄音與評測集。櫃台裝麥克風只錄不做事，人工整理 200 句真實對話與正確答案。這是之後所有準確率數字的基準。
第 1 階段 · 3 週
只顯示、不出單。平板即時顯示草稿單，櫃台照舊打 POS。每天對帳看命中率。目標：品項命中 ≥ 95%。
第 2 階段 · 2 週
櫃台確認後出單。接 POS（A 或 C），櫃台按確認才送。目標：確認→出單 < 2 秒，漏單 0。
第 3 階段 · 2 週
開快速通道。符合條件自動放行＋3 秒撤銷。目標：自動放行準確率 ≥ 98%、佔比 ≥ 30%。
第 4 階段
複製到岡山店。菜單差異只改設定，不改程式。
