理解層設計與菜單知識庫

兩件事在這一頁定案：一、理解層改成「Jev 直覺判斷 ＋ Gemini 抽取」雙模型，Jev 是 TypeSafe AI 的 System One 決策模型，不是 Gemini（前一份選型頁誤讀，已更正）。二、社守 POS 匯出的價目表已整理成理解層用的菜單知識庫。

2026-09-28知識庫來源：POS 價目表匯出 2026-09-28Jev 資料來源：TypeSafe 官方文件（頁尾）

1. Jev 是什麼、適合做什麼

不生成文字，只回答「典型化的判斷」

輸入一段 state（文字或結構資料），問它幾個事先定義好型別的問題，一次全部平行回答。三種問法：

  • Choice：從你列的選項裡挑一個（最多 255 個），附每個選項的機率與信心
  • Score：在你定義的 2～10 個等級上打分
  • Noul：這句話是真的嗎？回 0～1 的機率

快、便宜、信心分數是真的

  • 官方稱端到端 70～500 ms（美西機房；台灣打過去要再加約 150 ms 來回）
  • 輸入每百萬 token US$0.042，輸出免費。整天 2,000 次呼叫約 NT$3
  • 用 RLCD 訓練：信心高就真的比較準。LLM 自己報的信心分數做不到這點
  • 不可能輸出型別錯誤：答案一定在你給的選項裡

做不到的事（設計要繞開）

  • 不能生成字串：無法自己「寫出」一張點餐單，只能在你給的選項裡選
  • 一次 Choice 上限 255 個選項；菜單 303 品要分兩層問
  • 每個問題獨立評估，「第二個提到的餐點」這種相對指涉要靠問法設計
  • 目前是 early access，要排隊拿 key；公開端點約 8 個並發就會限流（一個櫃台夠用）
  • 中文能力官方未列，第 0 階段評測必測
官方自己的定位：「AI 版的 if 判斷式」——分類、路由、打分、抽取單一欄位、決定分支。點餐流程裡正好有一大堆這種判斷。

2. 理解層：一句話進來之後的路

輸入

定稿的一句話

誰說的、文字、目前草稿單（含編號）。

→
① Jev 門控 · 約 100 ms

這句話是什麼

意圖（點餐／修改／取消／同意／否定／閒聊）、提到幾個品項、客人是否在確認、櫃台是否在複誦。一次呼叫、七個問題平行回答。

→
② Jev 快車道 · 單品項

兩層 Choice 直接定位

先選分類（27 選 1）、再選品項（該分類 ≤ 23 選 1）、再問選項（每個選項群一題）。全部信心過門檻就直接套用，不經 Gemini。

→
③ Gemini 抽取 · 多品項或低信心

生成差異指令

gemini-3.8-flash，菜單放 context cache，結構化輸出 add／remove／set_qty／set_option／replace。

→
④ Jev 裁判 · 每條指令

校準過的信心

對每條指令問一個 Noul：「這句話是否真的要點〈品項＋選項〉？」機率就是平板上的黃底門檻與快速通道的放行依據。

→
輸出

指令＋信心

套用到草稿單、推到平板。

Jev（判斷）Gemini（生成）系統自己的程式
Jev 在哪一步問法為什麼是 Jev 不是 LLM
① 門控Choice 意圖 ×1、Choice 品項數（0／1／2／3+）、Noul 客人同意、Noul 客人否定、Noul 櫃台複誦中、Noul 提到選項、Noul 與點餐無關估計 3～4 成的話是閒聊或與點餐無關，100 ms 內先擋掉，Gemini 根本不用叫。狀態機的轉換（聆聽→核對→確認）全靠這幾個機率驅動。
② 快車道第一層 Choice 分類（27 項）→ 第二層 Choice 該分類品項 → 第三層每個選項群一題（單選用 Choice，多選每個選項一個 Noul），加數量 Choice（1～5）熟客一句「肉蛋吐司加起司」三次 Jev 呼叫 ≈ 0.5 秒完成，不用等 LLM 生成。這是「快速反應」需求的主要實現路徑。
④ 裁判對 Gemini 的每條指令問 Noul「原句是否明確要這個」；核對階段對每條草稿再問「櫃台複誦與此條一致」藍圖裡「信心 ≥ 0.9 才自動放行」這條規則需要一個校準過的數字。LLM 自報的 0.9 不是 0.9，Jev 的是。
兩個模型各做擅長的事。Gemini 負責「把一長串話變成結構」（生成），Jev 負責「這個判斷對不對、多有把握」（決策）。前一版把兩件事都塞給 Gemini，信心分數是它自己講的；現在信心來自一個專門為此訓練的模型。

5. 知識庫怎麼餵給三個模型

Gemini 語音辨識 · custom_vocabulary

上限 1,000 詞、建議 ≤ 100。取 clean_name 去重後約 150 個品名，用成本系統已有的 POS 銷售資料依銷量排序取前 100，再補「加起司、加蛋、不美乃滋、去邊」等高頻選項詞。

Jev · 每次呼叫現組選項

Jev 沒有快取概念，選項列表隨呼叫送。第一層 27 個分類名、第二層該分類品項（最多 23）、第三層該品項的選項群。每次 state 只放「這句話＋草稿單摘要」，約 300～600 token。

Gemini 抽取 · context cache

不把 2,639 個選項全塞進去。快取裡放「分類 → clean_name → 價格 → 哪些選項群」的精簡表（約 6k token），選項細節在指令送出後由程式驗證。快取儲存費每小時約 US$0.003。
